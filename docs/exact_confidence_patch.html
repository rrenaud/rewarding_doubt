Exact confidence: a minimal change to the released trainer

The released code teaches a model to state its confidence by sampling one confidence token after each answer and updating with PPO. Because the confidence is one of eleven short strings, its expected reward can be computed exactly instead. The patch adds that as --objective exact in Train.py, plus --objective exact_fast, which reads all eleven from one shared forward pass. Both keep the paper's reward, format penalty, KL controller, optimizer, LoRA setup, data and evaluation.

The idea

After the model writes Answer: …, Confidence, training only cares about what comes next: one of the eleven strings ": 0" … ": 10" followed by end of turn, or something malformed. PPO samples one of these, scores it, and estimates a gradient from that single sample with a learned value head as the baseline. The exact objective scores all eleven and weights each reward by the probability the model gives it.

What is optimized

For one answer, let p(k) be the probability the policy gives the completion ": k" + end of turn, and p_ref(k) the same under the reference model (the LoRA adapter switched off, which is what TRL uses as the reference for PEFT models). R(k) is the released QAResult_to_reward for confidence k; anything else gets wrong_format_penalty (−30).

J = Σₖ p(k)·R(k) + (1 − Σₖ p(k))·(−30) KL = Σₖ p(k)·log(p(k) / p_ref(k)) + p_other·log(p_other / p_other_ref) loss = −(J − β·KL) β = ppo_trainer.kl_ctl.value (the released adaptive controller) ∇J = Σₖ R(k)·∇p(k) − 30·∇p_other exact: no sample, no advantage, no baseline

J is exactly the quantity PPO estimates: the expected reward of the response the policy would sample. The KL term is computed over the same twelve outcomes rather than per sampled token, but it plays the same role, keeping the confidence distribution near the base model's, and it feeds the same adaptive controller.

Walking through the patch

1. Hooking into Train.py

The training loop already generates each answer up to the " Confidence" token. With --objective exact or exact_fast, the patch hands those answers to exact_confidence_step and skips the rest of the iteration: the second generation (the sampled confidence), reward computation for that sample, ppo_trainer.step, and log_stats. The default ppo path is untouched. The three hard-coded <|eot_id|> lookups become end_of_turn(tokenizer), which returns the same token on Llama-3.

2. Scoring the eleven completions

Each candidate is the tokenized ": k" plus the end-of-turn token. All eleven are appended to the same prefix and run as one padded batch; the log-probability of a candidate is the sum over its own tokens. Because candidates are scored as token sequences, a tokenizer that splits "10" into "1","0" (Qwen) needs no special case.

SingleAnswerSetting/util/ExactConfidence.py
def _level_logps(lm, prefix, candidates, pad):
    """log P(candidate | prefix) for each candidate token list, one batched forward."""
    seqs = [prefix + c for c in candidates]
    width = max(map(len, seqs))
    ids = torch.tensor([s + [pad] * (width - len(s)) for s in seqs], device=next(lm.parameters()).device)
    logits = lm(input_ids=ids).logits
    out = []
    for b, c in enumerate(candidates):
        span = logits[b, len(prefix) - 1:len(prefix) - 1 + len(c)].float().log_softmax(-1)
        out.append(span.gather(-1, torch.tensor(c, device=next(lm.parameters()).device)[:, None]).sum())
    return torch.stack(out)

Right padding with no attention mask is safe here: attention is causal and every position read comes before the padding.

3. Rewards and the reference, using the released code

For each answer that reached " Confidence", the patch parses it with the released response_to_QAResult, then calls the released QAResult_to_reward once per confidence level. So grading (exact match by default in the released code), the log-score scaling and the +2.5 bonus for a correct answer are whatever Train.py already uses. Answers that never reached " Confidence" are skipped: every completion of them is malformed, so the confidence has nothing to learn from them. The reference log-probabilities are computed once per step with the adapter disabled: per answer in exact, and for the whole batch in one call in exact_fast.

4. The objective

Probabilities of the eleven levels, the leftover mass for "anything else", the expected reward and the KL over those twelve outcomes. exact_fast passes in level log-probabilities it has already computed for the whole minibatch; exact scores the eleven sequences here.

    def objective(prefix, rewards, reference, logp=None):
        if logp is None:
            logp = _level_logps(lm, prefix, candidates, tokenizer.pad_token_id)
        p, p_ref = logp.exp(), reference.exp()
        p_other, p_other_ref = (1 - p.sum()).clamp(min=1e-8), (1 - p_ref.sum()).clamp(min=1e-8)
        expected = (p * rewards).sum() + p_other * wrong_format_penalty
        kl = (p * (logp - reference)).sum() + p_other * (p_other.log() - p_other_ref.log())
        return expected, kl

5. The update schedule mirrors PPO's

The released PPO configuration runs ppo_epochs = 4 passes over each batch of 8 in minibatches of mini_batch_size = 4: eight optimizer steps per batch. The exact step does the same with the PPO trainer's own optimizer (the same Adam over the same LoRA parameters), then feeds the mean KL to the same adaptive controller. Reusing data across passes needs no importance weights, because the objective is a deterministic function of the answer, not of a sample.

    model.train()
    stats = []

            losses = []
            for i, logp in zip(chunk, shared):
                expected, kl = objective(*rows[i], logp=logp)
                losses.append(-(expected - beta * kl) / len(chunk))
                if epoch == 0:
                    stats.append((expected.item(), kl.item()))
                if not fast:  # one backward per answer keeps the 11-sequence graphs small
                    losses[-1].backward()
            if fast:
                torch.stack(losses).sum().backward()
            ppo_trainer.optimizer.step()
    mean_kl = sum(kl for _, kl in stats) / len(stats)
    ppo_trainer.kl_ctl.update(mean_kl, config.batch_size)
    return [expected for expected, _ in stats]

6. exact_fast: one shared pass instead of eleven

The eleven strings ": 0" … ": 10" share everything up to the number. One forward pass over prefix + ": " therefore gives the probability of every number at its last position, from a single softmax: one sequence per answer instead of eleven, and the whole minibatch in one call. When "10" is two tokens (Qwen splits it into "1", "0"), the sequence also gets "1" appended, so the next position gives P("0" | "1") and splits level 1 from level 10:

p(10) = P("1")·P("0" | "1") p(1) = P("1")·(1 − P("0" | "1"))
def _shared_level_logps(lm, prefixes, levels, pad):
    """log P(": k" | prefix) for all 11 levels and every prefix, one forward pass (fast=True)."""
    n_common = 0
    while all(len(lv) > n_common + 1 for lv in levels) and len({lv[n_common] for lv in levels}) == 1:
        n_common += 1
    common, ends = levels[0][:n_common], [lv[n_common:] for lv in levels]
    two_token_ten = len(ends[10]) == 2  # Qwen: "10" is "1" "0"
    first = [e[0] for e in ends]
    seqs = [p + common + ([ends[10][0]] if two_token_ten else []) for p in prefixes]
    width = max(map(len, seqs))
    device = next(lm.parameters()).device
    logits = lm(input_ids=torch.tensor([s + [pad] * (width - len(s)) for s in seqs], device=device)).logits
    rows = []
    for b, p in enumerate(prefixes):
        n = len(p) + n_common
        logp = logits[b, len(p) - 1:n + 1].float().log_softmax(-1)
        common_logp = sum(logp[i, t] for i, t in enumerate(common))
        level = common_logp + logp[n_common, torch.tensor(first, device=device)]
        if two_token_ten:
            p_zero = logp[n_common + 1, ends[10][1]]
            level = torch.cat([level[:1], level[1:2] + torch.log1p(-p_zero.exp().clamp(max=1 - 1e-7)), level[2:10],
                               level[1:2] + p_zero])
        rows.append(level)
    return torch.stack(rows)

The one approximation. A level's probability here is P(": k"), without the end-of-turn token that exact includes. The end-of-turn sits one position after each number, a different place for each level, so a single shared sequence cannot read all eleven. "Anything else" therefore means malformed before the number, and stopping after the number is not trained. For this model and format it is close to certain anyway: malformed outputs stayed at 1.1%, the same as exact.

Checked against direct scoring. For three prompts, one at a time, every exact_fast level matched the same quantity computed by scoring each string token by token: largest difference 6 × 10⁻⁸ in probability on Qwen-2.5-3B and exactly 0 on Llama-3-8B.

7. Running on Qwen-2.5

The released code looks up Llama-3's end-of-turn token by name. Qwen-2.5 has no <|eot_id|>, so the lookup returns nothing and generation never stops at the end of the turn. The helper falls back to the tokenizer's own end-of-turn token (<|im_end|> for Qwen); the evaluation script gets the same one-line change.

def end_of_turn(tokenizer):
    """Llama-3's <|eot_id|>, or the tokenizer's EOS where that token does not exist (Qwen: <|im_end|>)."""
    eot = tokenizer.convert_tokens_to_ids("<|eot_id|>")
    return eot if eot is not None and eot != tokenizer.unk_token_id else tokenizer.eos_token_id

What changes and what stays

Unchanged

  • Model loading, 4-bit base, LoRA (r = 8)
  • Prompt, data loading, answer generation
  • Reward function, grading, −30 format penalty
  • Optimizer, learning rate, batch size, 8 updates per batch
  • Adaptive KL controller (initial 0.05, target 6)
  • Epoch checkpoints, evaluation and metrics

Replaced or removed

  • Sampling a confidence (a second generate per answer)
  • Value head and its loss
  • Advantage estimation (GAE) and whitening
  • PPO ratio clipping
  • Per-token KL on the sampled response → exact KL over the 12 outcomes

Both exact objectives skip the second generation PPO needs to sample a confidence, and run the same eight updates per batch. exact scores eleven full sequences per answer in each update; exact_fast scores one, which makes each iteration about 6.5 times faster than the released PPO. Part of that margin is the released PPO's own overhead: it computes a log-softmax over the whole vocabulary at every position, logs an entropy statistic, keeps gradient checkpointing on and clears the GPU cache every step. Removing those without changing the numbers made PPO about 4 times faster on Llama-3-8B in our runs, so against an optimized PPO the speedup would be closer to 1.5–2 times.

Caveats

  • The comparison is short: 256 steps on 1,024 questions. The paper trains about 85 times longer on the full training set, and its Qwen-2.5-3B AUROC (0.907) is well above both arms here.
  • Scores are on 512 test questions. At that size even a perfectly calibrated model averages ECE around 0.04, so ECE differences below that are not resolvable.
  • exact_fast leaves out the end-of-turn factor (section 6), so stopping after the number is not trained; the malformed rate was unchanged here, but longer training could show drift that exact would catch.
  • Answers are generated by the training policy (as released), so long training can change them; the exact objective does not penalize an answer that never reaches " Confidence", since that answer has no confidence to train.
  • The released reward grades answers by exact match, while the paper describes F1 > 0.5. Both arms use the released behaviour.
