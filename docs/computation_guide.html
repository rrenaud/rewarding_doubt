Three ways to reward doubt

The released Rewarding Doubt baseline and our two variants train the same thing: the confidence a model states after its answer. They share every step up to the point where that confidence gets scored. This guide shows where they split, what each one computes for a single question, and what each costs per step.

Released PPO (baseline) Discrete-exact Fractional

Where the computation splits

Every method runs the released code's front half unchanged. The current model reads a TriviaQA question and samples Answer: …, Confidence at temperature 0.6, stopping at the token Confidence. The released F1 grader then labels the answer correct (y = 1) or wrong (y = 0). The answer is never trained; only the few tokens after Confidence are.

Where each method pushes

The scores matter less than their gradients, which say how each string's probability should change. The panels show that push for the strings with any probability. Bars above the line make a string more likely; bars below make it less likely. Each panel is scaled to its own largest bar.

What one step costs

Each square below is one pass of the model over the full sequence for one question: prompt, answer and a confidence continuation, about 120 tokens. Sampling the answer is shared and cheap. The differences are in how many passes follow and whether they compute gradients.

In practice

  • Choose PPO when the output space is open. It needs only a reward for whatever the model wrote. That generality is why the paper uses it, and it handles format errors without help.
  • Choose an exact variant when the confidence comes from a fixed list. It removes sampling noise from the update and needs no reference model, value head or KL tuning. In our runs it reached the same calibration as the released PPO in about 60% of the training time.
  • Discrete-exact vs fractional is a choice about the output. Discrete-exact commits to one level, so a sampled reply prints the calibrated number. Fractional's target is the mean, which is best read from the 11 probabilities rather than from one sampled reply.
  • Implementation risk is lopsided. Our first PPO port, without a value head, calibrated far worse than the released code. The exact variants have two settings (hinge weight and threshold), and the same objective code runs on Tinker and on Modal.

Symbols

ℓ_k
Summed log-probability of the string ": k" plus the end-of-turn token, after the answer
π_k
ℓ renormalized over the 11 strings: the chance of stating k, given a valid confidence
R(p, y)
Clipped log score, y·log p + (1 − y)·log(1 − p), rescaled to [−1, 1]. The released code uses a ×10 scale with a +2.5 bonus for correct answers.
β
KL coefficient: 0.05 at the start, adapted toward 6 nats per sequence
GAE
Generalized advantage estimation: the reward minus the value head's prediction, carried back over the response tokens (γ = 1, λ = 0.95)
hinge
1.0 × relu(log 0.95 − log Σ e^ℓ_k): zero while the model puts at least 95% on valid strings
